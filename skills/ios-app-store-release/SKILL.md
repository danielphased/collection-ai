# iOS — App Store / TestFlight release

Each check below is a common cause of a rejected or failed upload. Run **all** of them before handing an archive to the account holder. Failing an upload costs a round-trip with a human at Xcode Organizer.

Project-specific rules (architecture, branches, ticket keys, device models) belong in the project's own CLAUDE.md or .claude/ — follow them when present.

## Facts to establish for the app (record them in the project's CLAUDE.md)

| Item | Where to find it |
|---|---|
| Team ID | Developer portal → Membership; `DEVELOPMENT_TEAM` build setting |
| Bundle ID | `PRODUCT_BUNDLE_IDENTIFIER`; must match the App ID |
| App Store Connect app | App record name, Apple ID, SKU |
| TestFlight group | Internal groups skip Beta App Review; external groups do not |
| Project | If `project.yml` exists, it is the source of truth and the `.xcodeproj` is generated by `xcodegen` — Xcode UI edits are lost. |
| Info.plist | If hand-written (`GENERATE_INFOPLIST_FILE: NO`), `INFOPLIST_KEY_*` build settings are ignored. |
| Archive | Project archive script or `xcodebuild archive`. Upload is done by the human through Organizer (or by script with an ASC API key). |
| AASA hosts | Each `webcredentials:`/`applinks:` host must serve an AASA containing `<TeamID>.<BundleID>`. |

## Build number bump

`CURRENT_PROJECT_VERSION` (`CFBundleVersion`) must be **strictly higher** than every build App Store Connect has seen for that marketing version. Bump it after **any** upload attempt that reached Apple, even a failed one. A date-based format such as `YYYYMMDDNN` (e.g. `2026102101`) keeps it monotonic. `MARKETING_VERSION` follows the release plan.

1. Find the current value: `xcodebuild -showBuildSettings -scheme <Scheme> | grep CURRENT_PROJECT_VERSION`.
2. Set the new value:
   - **xcodegen:** edit `CURRENT_PROJECT_VERSION` in `project.yml` (all targets that set it, including extensions), then `xcodegen generate`.
   - **Plain Xcode project:** `agvtool new-version -all <N>` (requires `VERSIONING_SYSTEM = apple-generic`), or edit every `CURRENT_PROJECT_VERSION = …;` in `project.pbxproj`.
3. App extensions must carry the same build number as the host app.
4. Confirm in the archive (check 11).

## Pre-upload checklist (blocking)

1. **App icon is opaque.** `sips -g hasAlpha <AppIcon.appiconset/*.png>` must say `hasAlpha: no` for every file. Transparency triggers "Invalid large app icon … alpha channel". Flatten it onto an opaque background, with roughly 12–15% padding so the iOS corner mask doesn't clip the mark.
2. **Export compliance keys are consistent.** If the app ships non-exempt crypto (custom or non-standard algorithms beyond what the OS provides):
   - If App Store Connect has issued an **ITSEncryptionExportComplianceCode** (App Information → App Encryption Documentation): set **both** `ITSAppUsesNonExemptEncryption = YES` and `ITSEncryptionExportComplianceCode = <code>`.
   - If there is no code yet: **omit both keys**, and the account holder answers the questions per build in App Store Connect. `YES` without a matching code fails validation ("Invalid Export Compliance Code … value []").
   - **Never set `NO`** for such an app. That would be a false declaration.
   - Answering the questionnaire is the account holder's legal decision. Never answer it on their behalf.
3. **Privacy manifest** `PrivacyInfo.xcprivacy` is present in the built `.app`.
   - It declares every required-reason API actually used (e.g. UserDefaults `CA92.1`).
   - Re-grep for file timestamps, system boot time, disk space and active keyboards whenever code changes.
   - New SPM dependencies must ship their own manifests.
3a. **Check native binaries for required-reason API symbols.** Run `nm -u` on the app binary and on every embedded framework, especially prebuilt Rust/C/C++ cores. Map each symbol to its manifest declaration:

| Symbols | Category | Reason |
|---|---|---|
| `stat`/`fstat`/`lstat`/`getattrlist` | File Timestamp | C617.1 |
| `mach_absolute_time`/`systemUptime` | System Boot Time | 35F9.1 |
| `statfs`/volume capacity | Disk Space | E174.1 |
| `UserDefaults` | User Defaults | CA92.1 |

Native cores frequently import `_fstat` without anyone noticing; if so, C617.1 must be declared.
4. **Build number** has been bumped per the procedure above and is higher than any build App Store Connect has seen.
5. **Entitlements ⊆ App ID capabilities.** Every key in the app's `.entitlements` must have its capability enabled on the App ID in the developer portal:
   - `associated-domains` → Associated Domains
   - `aps-environment` → Push Notifications
   - NFC reader-session formats → NFC Tag Reading

   Extra capabilities on the App ID are harmless. Missing ones break the signing profile.
6. **Orientations.** iPad builds declare all four orientations in `UISupportedInterfaceOrientations~ipad`, or set `UIRequiresFullScreen`. Otherwise Xcode warns and upload validation can fail.
7. **Associated domains for distribution.** TestFlight and App Store builds ignore `?mode=developer`, so the test or production RP host needs a plain `webcredentials:` entry, and its AASA must be reachable via Apple's CDN (`https://app-site-association.cdn-apple.com/a/v1/<host>`).
8. **No descoped capabilities linger.** Entitlements, App Groups, VPN or external-accessory protocols that the project has removed must not be re-added without a decision.
9. **`aps-environment`** is usually `development` in source. Export with automatic signing rewrites it to `production`. Verify that on the Organizer review screen.
10. **dSYMs.** "Upload Symbols Failed … <Framework>.framework" for a prebuilt binary framework is a **warning** and does not block upload. The proper fix is to build that framework with debug info and ship its dSYM (`dsymutil`). Track it, but don't block a beta on it.
11. **Archive metadata check:** read `PlistBuddy -c "Print :ApplicationProperties:CFBundleIdentifier"` (plus `CFBundleShortVersionString` and `CFBundleVersion`) from the archive's `Info.plist`, and confirm the signing team matches the project's Team ID.

## Claim discipline in App Store Connect text

TestFlight "What to Test", the description and review notes must never claim certifications or validations the product does not hold (e.g. "certified", "FIPS-validated", regulatory compliance). Describe what the product does, not what it has not been certified for. Include any tester warnings the product requires (e.g. single-active-device behaviour).

## Environment gotchas

- `xcodebuild` with a specific simulator `-destination` can hang in `actool` (asset-catalog thinning). Use `-destination 'generic/platform=iOS Simulator'` for build checks.
- If PIL or ImageMagick are unavailable, do image work (icon flattening) with a small Swift + CoreGraphics script (ImageIO and UniformTypeIdentifiers) or `sips`.
